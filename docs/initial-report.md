# 基于小型语言模型与输入法候选重排的中文拼音输入系统

## 摘要

本文设计一种利用左侧输入上下文重排中文拼音候选的原型。系统以 Rime 生成候选，以小型因果语言模型估计候选条件概率，再将模型分数与原始候选排序组合。数据来自本地清洗后的中文网页、评论和对话语料。210 例自动构造的测试样本中，前 20 候选召回 104 例；Rime 首选命中 93 例，组合方法命中 96 例，差异未达统计显著。实验说明方法具备原型可行性，但尚不能证明输入体验得到稳定改善。

**关键词：** 中文输入法；拼音转汉字；候选重排；小型语言模型；上下文消歧

## 1 背景与问题

无声调拼音对应大量同音汉字和词语，仅依赖词频容易忽略当前句子的语义。输入法同时受本地资源和响应时延约束。本项目研究在固定词典候选池上，约 15M 参数的小模型能否利用最近输入的文本改善候选顺序。

## 2 相关方法

Rime 提供拼音解析、词典查询和候选界面。VimeML 在日文输入法中使用词典提供的候选和因果语言模型进行重排 [1]。本项目将这一系统思路用于中文，并研究长度归一化及原始排序与上下文分数的组合。该组合是面向本系统的工程与实验设计，不能据此声称相关思想为首次提出。

## 3 数据与方法

数据导出 `zh-v13-export-r1` 的训练部分包含网页、评论和对话。按来源配额抽取约 8000 万、1000 万和 1000 万汉字，固定随机种子为 20261110。抽样记录与 SHA-256 位于 `data/manifest.json`。抽样按随机分片、行组及行顺序执行，不能解释为对全语料独立同分布均匀抽样。

模型为 6 层因果 Transformer，宽度 400，8 个注意力头，最大上下文 128，SentencePiece 词表 8192；输入与输出嵌入共享，实际参数量为 14,880,000。训练样本共 95,891,292 个 token，在 RTX 3080 Ti 上训练 20,000 步，训练环节耗时约 851 秒（不含分词器和编码准备）；最后一次训练批次损失为 5.228，不能作为泛化指标。候选分数为候选 token 的条件对数概率之和，按 token 数的指数幂归一化；将候选池内的归一化语言模型得分与基于候选原始顺序的线性先验加权组合。开发集显示直接重排容易将单字部分候选排到完整短语前，因此增加同字数候选仅在其原有位置内交换的限制；此约束是按开发集观察提出的探索性设计。开发集搜索权重 {0, 0.25, 0.5, 0.75, 1}、长度指数 {0, 0.5, 1} 和是否限制同字数，选择权重 0.5、指数 0、启用限制。上下文和候选分别分词，边界处与联合分词可能不同，是本实现的一项局限。

## 4 系统实现

小狼毫提供 Windows 输入法接入；Lua 过滤器收集至多 20 个候选，通过回环地址或临时文件请求本机推理服务，并按返回顺序输出。服务异常时保持原有排序。上下文仅来自输入法会话中的提交记录，不读取应用已有文本；会话上下文上限 128 个字符。临时文件包含编码后的上下文，异常退出时可能残留。Windows 中各通道的实际兼容性、时延以及快捷键行为仍需实机验证。

## 5 实验设置与结果

隔离 Rime 环境使用朙月拼音产生固定候选池；网页和评论验证数据按文档键划分开发与测试，对话使用原验证和测试文件。每个集合各含三个来源，每个来源 70 例。目标为保留文本中截取的 2–4 字片段，拼音由自动工具生成，不等同于人工输入日志；切片和多音字错误可能影响任务难度。数据清洗输出本身的文档级、跨来源和近重复独立性尚未得到证实。

候选池由隔离的 Ubuntu librime 1.7.3 与该发行版朙月拼音词典生成，桌面集成测试使用 Windows 小狼毫 0.17.4；两者版本和词典可能不同，离线结果不等同于 Windows 实际候选效果。训练语料来自随机选中的一个网页分片、一个评论分片和对话分片，来源分布不代表完整语料。

对照包括 Rime 原始排序、无上下文模型、上下文模型及加权组合；指标包括候选召回、全流程 Top-1/Top-5、目标存在于候选池内时的 Top-1/Top-5 和配对精确检验。候选池生成后，开发集用于选择权重及长度指数，测试集用于评价。

| 方法 | Top-1 命中 / 210 | Top-5 命中 / 210 |
|---|---:|---:|
| Rime 原序 | 93 | 102 |
| 模型，无上文 | 2 | 8 |
| 模型，有上文 | 5 | 16 |
| 组合，无上文，同字数限制 | 94 | 见结果文件 |
| 组合，有上文，不限制字数 | 19 | 见结果文件 |
| 组合，有上文，同字数限制 | 96 | 103 |

测试集目标位于前 20 个候选的有 104 例，召回率 49.52%；剩余 106 例不能由重排修复。在候选存在时，Rime 和组合方法 Top-1 分别为 93/104（89.42%）和 96/104（92.31%）。组合方法修正了 5 例、使 2 例变错，双侧配对精确检验 p=0.453125，差异不显著。网页、评论、对话三个来源的 Top-1 分别从 26/70、29/70、38/70 变为 28/70、30/70、38/70。无上文组合为 94/210，差异过小，不能证明上下文贡献；不限制字数时 19/210 表明部分候选的处理对本基准很敏感。测试结果及逐例预测见 `benchmark/test-results.json`。

例如，`bai'yi` 的目标“百亿”由原首选“白衣”改为正确候选；`na'li` 的目标“那里”由“哪里”改为正确候选。反例中，`ji'po` 的正确首选“击破”被改成“挤破”；`de'shuai` 的“的帅”被改为“的书”。后者提示相同字数也不能保证候选覆盖相同输入范围，后续应直接利用 Rime 的分段覆盖信息进行分组，并以人工标注样本复核。

Windows 本机 CPU 服务在 20 次、20 候选、6 字上文的临时文件往返测试中，中位数 61.1 ms、最大值 62.4 ms，服务进程树工作集约 313.6 MiB；126 字上文同样条件下中位数 326.8 ms、最大值 357.2 ms。每组只有 20 次，不能代表真实打字的尾延迟。Lua 过滤器超时为 150 ms，因此长上下文下容易回退原序；模型文件为 59,541,074 字节。隔离 Windows librime 测试验证了 Lua 过滤器和模拟服务的排序交互；本机实测服务分别验证了 socket 与临时文件通信，尚未完成记事本等实际应用的自动上屏验收。

## 6 分析与局限

候选不在池内时，重排器无法给出正确结果，必须单独报告召回率。由文本自动构造的候选与真实输入行为不同，开发/测试规模也较小，结果不宜外推至所有用户。现有数据导出清单没有完整列明源语料许可，发布数据或模型前需进一步核查。当前未完成 Windows 端到端桌面验收。
